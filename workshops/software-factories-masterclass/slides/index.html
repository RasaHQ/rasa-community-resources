Part A: concepts

A software factory turns a written task into a verified change.

  • A person writes what is wanted, in words a machine can act on.
  • A builder makes the change in an isolated copy.
  • An independent check judges it, and a decision is recorded.
Part A, concepts, 25 minutes. Drawn from the course Towards Dark Software Factories, in its Rasa form. Content owner: the writing seat.
Part A: concepts

In a dark factory, people write the task and the acceptance and do not review the code.

  • The effort moves from reading changes to writing what must be true.
  • The gates decide. Only an escalation asks a person.
  • Dark means no routine human reading, not no human responsibility.
Part A: concepts

The protected acceptance is written before any code, and the builder never sees it.

  • It is the holdout: the builder cannot tune its work to a test it cannot read.
  • It is pinned by a SHA-256 hash in the task, so the decision says which suite ran.
  • An edit to a protected file is an automatic REJECT.
Part A: concepts

Every decision is recorded with its evidence: the suite hash, the diff and the exit code.

  • ACCEPT integrates the change by itself.
  • REJECT names the failing check, so the builder can try again.
  • Exit codes: ACCEPT 0, REJECT 1, could not run 2, not ready 3, escalate 4.
Part A: concepts

The platform is reused and only the product changes.

  • The card contracts, the renderer and the source readers already exist and are already accepted.
  • The factory changes the product only, which is why the good change to the market card is one line.
  • The lesson is the gates, not the code.
Part A: concepts

A gate proves only what it checks, so know its limits.

  • Our suite runs the candidate with no network and judges only the card it returns.
  • A candidate that printed a hand-made valid card for every scenario would still pass.
  • That is why the checks are specific, the pins are recorded and a person still decides when to go dark.

Part B: Rasa Mantle

A skill is a markdown file that tells the agent what it can do and when to ask first.

  • Tools come from your own code or from an MCP server.
  • A tool that cannot be undone can require the caller's confirmation, and the engine enforces the wait.
Part B: Rasa Mantle

Tools are imported from MCP servers, so the agent can use a service without new engine code.

  • In the briefing agent, one skill imports one tool from a local service.
  • The service returns the four cards, and the agent's words never become the card values.
Part B: Rasa Mantle

The inspector lets you talk to the agent and watch what it did.

  • Run it with rasa inspect and chat in the browser.
  • It shows the tool calls, so you can check the agent used the service and not its own memory.
Part B: Rasa Mantle

Voice is an input to the same agent, and it is optional.

  • With a Deepgram key the agent takes spoken requests. Without one it works in text.
  • Keys and the licence are read from your environment only, and the doctor shows SET or MISSING, never the value.

OpenAI runs the agent loop, and you run your own functions.

  • One call starts a session. This is not the separate openai-agents package.

Part C: OpenAI Agents API

An agent is a model, instructions and tools.

  • The model name must be one the Agents API supports. In our rehearsal gpt-4.1-mini was rejected with HTTP 400, model not supported.
  • Use the model named in OpenAI's own guide.

Official documentation: Configuration

Part C: OpenAI Agents API

Function tools are your code, described by a closed schema.

  • A declaration has a name, a description and a JSON Schema with additionalProperties set to false.
  • The model never runs your code. It asks, your function runs on your machine, and the result goes back.
Part C: OpenAI Agents API

The handlers you register are the allowlist.

  • A function the model asks for that you did not register stops the run.
  • A handler returns a refusal and does not raise, because the SDK swallows exceptions.
Part C: OpenAI Agents API

The environment decides what the agent itself can touch.

  • The choices are none, OpenAI-hosted and self-hosted. Your function tools run on your side whatever you pick.
  • For a tightly confined builder choose the smallest option.

Official documentation: Environments

Part C: OpenAI Agents API

A turn is a stream of events, and the answer is a result.

  • Events include the session created, the turn started, a function action required, a tool result, output text and the turn ending.
  • zeocore reads the stream and returns the status, the output text, the tools called and a short error code.

Official documentation: Events

Part C: OpenAI Agents API

Everything is bounded, and a breach is never reported as success.

  • Calls per turn, events, a whole-run deadline, a per-read timeout, argument size and result size are all limited.
  • A breach returns incomplete with a fixed code, never provider text and never a key.

Official documentation: Manage sessions

Part C: OpenAI Agents API

The key stays in the environment.

  • The OpenAI client reads OPENAI_API_KEY from your environment. zeocore never accepts, stores or logs it.
  • Show SET or MISSING, never the value.

Official documentation: Observability

Part C: OpenAI Agents API

Your code decides what is true, not the model's prose.

  • Build what you display from what your handlers returned, never from the model's output text.
  • In the factory, the gates read the scratch copy and not the builder's words.
Part C: OpenAI Agents API
