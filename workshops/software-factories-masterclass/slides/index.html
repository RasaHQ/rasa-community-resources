Part A: concepts

A software factory takes a task, makes the change in an isolated copy, checks it and records a decision.

  • Task, in a file.
  • Change, in an isolated copy.
  • Check, by a protected suite.
  • Decision, recorded.
A software factory is a small loop with four parts. It takes a task. It applies a change in an isolated copy of the code. It checks the change with a suite the builder never sees. And it writes down its decision. In the course that loop fits in one short Python file, and in this class it's the same loop pointed at a Rasa Mantle project. Keep these four words in your head, because every later slide adds one rule to one of them.
Part A: concepts

A dark software factory is one where the evaluation is the only review.

  • No person reads every diff.
  • The suite is the review.
  • So the suite has to be right.
The phrase dark factory comes from factories that run with the lights off, because nobody needs to be in the room. For software it means people stop reading every change. That sounds reckless until you say what replaces the reading, which is the evaluation. If the evaluation is the only review, then everything depends on the evaluation being protected and being honest. Our claim is that you earn each step toward it with evidence, and we'll show how.
Part A: concepts

Protected acceptance is a suite the agent can't edit, written before any candidate exists.

  • Written first, from the task.
  • Pinned by its hash.
  • The builder never sees it.
The first rule is about the suite. It's written before any candidate exists, from the task text alone. It's pinned by a hash, so changing a single byte changes the hash and everyone can see. And the builder never sees it. Here's why this matters. An agent that can edit its own check will pass it. That has names, specification gaming and reward hacking, and in the pack you'll run today there's a candidate that tries exactly that. The gate rejects it before any suite even runs.
Part A: concepts

A change is made in an isolated copy, and only what changed becomes the candidate.

  • A scratch copy of the product.
  • A list of allowed paths.
  • The diff is the candidate.
The builder works in a scratch copy, so nothing it does can touch the real product or the suite. The task lists the paths it may change, and anything outside that list is refused. What comes out is the diff, the exact set of changes. The agent's own summary still gets recorded, next to the diff and labeled a claim. A reviewer gets the diff, the verdict and the numbers, so a person can decide without trusting the agent's prose.
Part A: concepts

Independent verification means the verdict comes from checks the builder could not influence.

  • The checker runs apart from the builder.
  • It reads the change and ignores the story.
  • Same checks for every candidate.
Independent verification has a simple test. Could the builder have influenced this check? If the answer is yes, it isn't verification. So the checker runs in a separate process from the candidate's code, it reads the change and ignores the story, and it runs the same checks on every candidate. In the pack, the candidate runs in a child process, and the process that decides never executes the candidate's code. We'll say the limit out loud as well. A determined forger could still rebuild a valid answer, so the suite and its pins are a gate. They don't claim to be a proof.
Part A: concepts

The decision has more than two answers, because a missing package isn't a wrong change.

  • ACCEPT: the change passed.
  • REJECT: the change failed a check.
  • NOT READY: it couldn't be judged here.
Most people picture two answers, pass or reject. Real runs need a third. If a candidate imports a package your machine doesn't have, it couldn't be judged here, which is a different thing from a wrong change. If you record it as a rejection, your numbers lie. So the factory keeps three outcomes apart and gives each its own exit status. A person reading a log can tell a missing package from a wrong answer, and a script reading an exit code needs the same help.
Part A: concepts

Two correct changes can still break each other, so integration replays every earlier promise.

  • Each change passes alone.
  • Shipping the second can erase the first.
  • Refuse a stale base, replay the old checks.
Here's a trap that appears the moment two agents work at once. Each agent does exactly what its task asked, and each passes its own suite. Then you ship the second change, and it silently undoes the first. Neither change was wrong. The mistake is in how they were combined. The fix is an integration step that refuses a stale starting point and replays every earlier promise before it lets anything in.
Part A: concepts

A release ships the exact bytes that were tested, with an approval the builder can't give.

  • Bind the release to the tested digest.
  • A person the builder can't add approves.
  • One command goes back.
Accepted isn't the same as released. Between those two words there are three ways to go wrong, and all three are about identity. You could ship a different thing than the one you tested. You could ship on the say-so of someone who had no right to give it. Or you could find out afterward that what's running isn't what you released. So a release is bound to the digest the factory tested, it needs an approval from a person the builder can't add to the list, and you can go back with one command.
Part A: concepts

People write the specification and the acceptance, and the factory reuses the same platform for every task.

  • The task is a spec plus a hidden suite.
  • The platform stays the same.
  • People spend their time on the spec.
Here's where the human effort goes in a dark factory. Each new task is a specification and a protected suite. That's the part people write, and it's the hard part. Everything else is the platform, which you build once and reuse. It's the isolated copy, the gates, the integration step and the release step. So people stop reviewing every line of code and start reviewing the thing that decides whether code is good. Today's second act shows it, because you'll see a new task go through a platform that already exists.
Part A: concepts

Eighteen accepted runs out of eighteen give a lower bound of 0.82, so they don't support a pass rate of 90 percent.

  • 18 of 18 accepted.
  • Wilson 95% interval: 0.82 to 1.00.
  • 35 clean runs are needed for a lower bound of 0.9.
Let's look at what a perfect record really tells you. In the pack there are eighteen recorded runs by two coding agents, and all eighteen were accepted. That sounds like one hundred percent. With a ninety-five percent Wilson interval, eighteen out of eighteen gives a range from 0.82 to 1.00. To claim a lower bound of 0.9 you need thirty-five clean runs. So a short perfect record is encouraging, and it still isn't a pass rate. A count needs an error bar before anyone makes a decision on it.
Part A: concepts

Supervision is reduced by a written policy, where evidence earns one step and one escaped defect takes it back.

  • The policy is a file.
  • Evidence earns a step.
  • One escaped defect demotes.
When may a person stop reading each change? The wrong answers are a feeling, a deadline, or the agent's own record of itself. The right answer is a written policy. It says what evidence earns less supervision, what takes it back, and who may change the policy. In the course, promotion is tied to a measured lower bound, and one escaped defect demotes you. The policy file also refuses any proposal that edits the gate approving it, so the factory can't promote itself.
Part A: concepts

When attempts run out or the evidence is thin, the factory stops and calls a person.

  • A stall is retried, within a limit.
  • The same decided request is not run again; a revised candidate is a new attempt.
  • Then it escalates to a person.
Failure comes in more kinds than a wrong change. A candidate can run forever. The factory itself can crash in the middle. The same request can arrive twice because a network call timed out. If you treat all of those as rejections, your numbers lie. If you retry everything, you rerun real rejections and you might leak the suite one attempt at a time. So a stall is retried within a limit, the same decided request is never run again, a revised candidate is a new attempt, and when the attempts run out a person gets called.
